Isagawa Kernel

A self-building agent harness with hook-enforced governance.

The kernel agents build inside. Hooks fire at tool-call boundary and physically block bad actions. An anchor forces re-grounding every N actions. A learn cycle turns each failure into a mechanical rule update. 29 lessons recorded so far: each one is now enforced as code, not as instructions.

View on GitHub → alain@isagawa.co

The loop

session-start -> anchor -> WORK -----------------> complete
                   ^         |                       ^
                   `-- every 10 actions <-----------'
                             |
                   failure? -> fix -> learn (MANDATORY)

Every working session runs this loop. The agent cannot bypass any step: hooks block writes until each gate passes.

Why a harness?

Agents drift. Mid-task they forget what they were doing, skip steps they read minutes ago, and rationalize shortcuts as "more efficient." Prompts don't fix this: the model has already proven it will read the instruction, agree, and then violate it.

A harness fixes this mechanically. The kernel's hooks intercept every tool call and check state. Counter at N actions? Block until anchor runs. Test failed? Block until lesson is recorded. The agent isn't asked to behave; it's structurally prevented from misbehaving. Same outcome as discipline, without depending on discipline.

The 29 recorded lessons include three for the same anchor-skip pattern: proof that human discipline failed three times until the kernel mechanically enforced the rule.

Architecture

Four moving parts. Each one solves a specific failure mode.

LayerWhat it doesFiles
Hooks Fire at tool-call boundary. Block writes when state preconditions fail. Append every action to an audit log. universal-gate-enforcer.py, sr_dev-gate-enforcer.py, actions-log-appender.py, test-failure-detector.py
Commands Kernel operations the agent must invoke (anchor, learn, complete, backlog). Skill-based: agent calls them through a Skill interface, never directly. /kernel/anchor, /kernel/learn, /kernel/complete, /kernel/backlog, /kernel/execute-pipeline, /kernel/session-start
Skills Multi-step capabilities (autonomous cycling, task building, production testing, audit workflow). Each skill is an indexed file structure: entry point plus step-by-step references. autonomous-cycling, task-builder, execute-pipeline, prod-test, audit-workflow, kernel-domain-setup
State Workflow JSON, intent chain, anchor logs. Append-only where it matters (audit trail), mutable where it doesn't (session counters). .claude/state/*

Two-tier governance

Hooks alone are too rigid. Protocol alone is too soft. Both are necessary.

Tier 1 is mechanical. Hooks fire at tool-call boundary. If state says "needs_learn: true," every write is blocked until /kernel/learn runs. The agent can't talk its way past a hook: the hook isn't reading instructions. It's reading bytes.

Tier 2 is behavioral. Every 10 actions, the anchor command forces the agent to re-read the protocol, re-read the lessons, and apply specific rules to its next action with concrete verbs. Protocol drift is a guaranteed failure mode in long sessions; the anchor reverses it on a schedule.

Hooks alone would require encoding every conceivable rule in code: impossible for a self-improving system. Protocol alone would rely on the agent following text it has already proven it will violate. Together: hooks for the rules you can enforce mechanically, protocol for the rules you can't. The 29-lesson file is exactly the seam between them. Every entry is either already a hook or a candidate to become one.

Every backlog item is hash-signed. The raw_input_hash is the SHA-256 of the user's words at invocation time. The backlog_hash_after is the SHA-256 of the resulting file. Both go into an append-only chain that any third party can verify.

Lesson recording

## 2026-06-08 Agent Bypassed /kernel/backlog Skill for Backlog 129 (Batch Trigger)
- Issue: During a multi-item response ("yes" to memory + backlog 129 + re-anchor
  offer), agent created backlog 129 by directly calling intent.py record followed
  by a direct Write. The /kernel/backlog skill was not invoked.
- Root Cause: Three compounding factors. (1) Batch trigger: the agent treated "yes"
  as approval for a batch of three actions and optimized the middle one for speed.
  (2) Recovery context bleed: earlier in the session the agent had legitimately called
  intent.py record for 127 and 128 as part of rename-recovery after a pull collision -
  calling intent.py felt "already in use." It wasn't. Rename recovery and new-backlog
  creation are different operations. (3) Familiarity bias: agent had just re-read the
  lesson in the anchor 10 minutes prior and still committed the violation.
- Fix: Acknowledge the violation at the next anchor, set needs_learn: true, record the
  lesson, file a follow-up backlog for mechanical enforcement.
- Recurrence pattern: This is the SECOND time this exact failure has been recorded
  (first: 2026-04-25 with backlog 047). Two recurrences means human discipline has
  failed and mechanical enforcement is overdue.
