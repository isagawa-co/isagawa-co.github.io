A self-building agent harness with hook-enforced governance.

Hooks at the tool-call boundary. Anchors that force re-grounding every N actions. Learn cycles that record each failure as a rule the system enforces mechanically where it can, and re-reads at every anchor where it can't.

The Problem

Agents drift. Forget. Skip steps. Prompts don't fix it.

Mid-task they forget what they were doing. They skip steps they read minutes ago. They rationalize shortcuts as "more efficient." The model has already proven it will read the instruction, agree, and then violate it. Telling it harder doesn't work. Asking nicely doesn't work. The fix has to be structural.

  • How do you stop an agent from skipping a checkpoint it just read about?
  • How do you make the system catch its own failures, even when the agent thinks it didn't fail?
  • How do you keep behavior consistent across hour-long sessions and context compression?

The Loop

Every session runs the same loop. No step can be skipped.

session-start, anchor, work, complete. The same cycle, every session. Anchors fire every N actions. Failures trigger a mandatory learn step. State survives restarts. Context survives compression. The loop itself is hook-enforced. Specific rules within it land in one of two tiers: hooks where they can, protocol re-read at every anchor where they can't.

session-start -> anchor -> WORK -----------------> complete
                   ^         |                       ^
                   `-- every 10 actions <-----------'
                             |
                   failure? -> fix -> learn (MANDATORY)

run-task.sh is the cycling driver. It spawns a fresh claude -p process per task. Each one reads CLAUDE.md, runs session-start and anchor, picks the next incomplete task, executes it, marks complete, exits. State on disk provides continuity between runs. /kernel/autonomous-cycle kicks off the loop; /kernel/execute-pipeline wraps the full flow from backlog item to final commit. The user shorthand for this whole pattern is just "the loop."

Smart gates. When a hook blocks an action, the error message names the exact command that fixes it. "Blocked: 30 actions since last anchor. Token: 3e65b1c5. Invoke /kernel/anchor to re-center, then retry." The agent doesn't need to figure out how to comply: the hook tells it, and the same hook verifies the fix landed.

The Architecture

Four moving parts. One harness.

Each part solves a specific failure mode. Together they reduce the surface area where the agent has to be trusted to follow text it has already proven it will violate.

1

Hooks (6)

Fire at the tool-call boundary. Block writes when state preconditions fail. Auto-increment the anchor counter on every Write/Edit/Bash. Append every action to an audit log. Detect non-zero test exits and set needs_learn. Block inline task execution to force run-task.sh isolation. For rules wired to a hook, the hook isn't reading instructions: it's reading bytes.

2

Commands (15)

The kernel's verbs. session-start, anchor, learn, complete, backlog, fix, task-builder, execute-pipeline, autonomous-cycle, audit-workflow, prod-test, attest, domain-setup, reset. The agent invokes each via the Skill interface, never directly: each command enforces template structure and intent-chain attestation. /kernel/execute-pipeline is the user-facing entry into the autonomous loop.

3

Skills (7)

Multi-step capabilities. autonomous-cycling, task-builder, execute-pipeline, prod-test, audit-workflow, kernel-domain-setup, website-cloner. Each skill is an indexed file structure: entry point plus step-by-step reference files the agent reads at execution time. Steps are atomic: one step writes one file.

4

State

workflow.json, session_state.json, actions.jsonl, anchor-logs/, intents/, attestations/. Append-only where it matters (audit trail, intent chain, anchor logs, Sigstore/Rekor bundles). Mutable where it doesn't (session counter, current task). Hash-signed for cross-machine verifiability.

Design Patterns

The patterns the rest of the kernel rests on.

Five conventions that show up across commands, skills, hooks, and lessons. Each one is a recorded rule, not a vibe.

Wikilink tiered indexing

Parent files are indexes. When any subtopic crosses ~50 lines of detail, it extracts to its own reference file and the parent links to it as → [[references/file.md]]. SKILL.md, workflow.md, step files, protocol, lessons all follow this. Files stay scannable. Detail is one link away, never inlined.

Atomicity

One task equals one action. Copy 11 files is 11 tasks. Setup plus run plus verify is 3 tasks. "Merge if small" was a rule the kernel had, and it became a lesson: bundling produces violations every single time. Small tasks are correct tasks.

L1/L2/L3 testing

Every deliverable plans three test tiers during atomization, not at execute time. L1 (does it exist? grep, file_exists). L2 (does it run? exit code). L3 (does it produce correct results in a real scenario? spawn the kernel loop and verify output). "Simulated" is never L3.

Multi-domain

/kernel/domain-setup builds a fresh protocol plus per-domain hooks for any project. One project equals one domain equals one protocol. Extend via /kernel/learn, never recreate. The kernel is portable: drop it in a new repo and it builds its own enforcement layer for that repo's verticals.

Self-audit

/kernel/audit-workflow scans the kernel's own infrastructure for gaps: missing commands, broken skill references, hooks not wired in settings, protocol drift, stale state, incomplete L1/L2/L3 coverage, task atomicity violations. Findings generate fix tasks. Tasks auto-execute. The kernel keeps itself current.

Design Decision

Two-tier governance. Mechanical and behavioral.

Hooks alone are too rigid. Protocol alone is too soft. Both are necessary. The 29-lesson file is exactly the seam between them: every entry is either already a hook or a candidate to become one.

Tier 1: Mechanical

Hooks fire at the tool-call boundary. If state says needs_learn: true, every write is blocked until /kernel/learn runs. No talking past it. No prompt engineering past it. No editing state files to bypass it: that path is itself a hook-blocked write.

Tier 2: Behavioral

Every 10 actions, the anchor command forces the agent to re-read the protocol, re-read the lessons, and apply specific rules to its next action with concrete verbs. Protocol drift is a guaranteed failure mode in long sessions. The anchor reverses it on a schedule.

Hooks alone would require encoding every conceivable rule in code: impossible for a self-improving system. Protocol alone would rely on the agent following text it has already proven it will violate. Together: hooks for the rules you can enforce mechanically, protocol for the rules you can't.

Receipts

The system writes down its own failures.

An anchor catches a self-detected violation. The intent chain hashes the user's words. A recorded lesson flags a candidate for mechanical enforcement after recurrence, if the rule can be hooked at all. All three are append-only artifacts from this workspace.

.claude/state/anchor-logs/2026-06-08/06-45-00Z.json 
{
  "anchor_timestamp": "2026-06-08T06:45:00Z",
  "actions_count": 48,
  "violations_found": 1,
  "violation_details": [
    "Backlog 129 created via direct intent.py call,
     bypassing /kernel/backlog skill."
  ],
  "needs_learn_set": true
}

Every anchor archives the actions reviewed and any violations found. When backlog 129 was created by bypassing the /kernel/backlog skill, the next anchor flagged it and set needs_learn: true. The agent could not write again until the lesson was recorded.

.claude/state/intents/131-intent-chain.jsonl 
{
  "rev": 1,
  "timestamp": "2026-06-08T07:24:57+00:00",
  "raw_input_hash":     "0c43483511fb6ee241b34fc58c294751...",
  "backlog_hash_after": "6f9ebac571cb3369ee518f1d04432458..."
}

Every backlog item is hash-signed. raw_input_hash is the SHA-256 of the user's literal words at /kernel/backlog invocation time. backlog_hash_after is the SHA-256 of the resulting file. Both go into an append-only chain a third party can verify.

.claude/lessons/kernel-compliance.md 
## 2026-06-08 Bypassed /kernel/backlog
- Root cause: batched "yes" trigger, agent
  optimized middle item for speed
- Recurrence: 2nd time recorded
  (first: 2026-04-25 with backlog 047)
- Escalation: mechanical enforcement via
  PreToolUse hook now overdue

When the /kernel/backlog bypass happened a second time, the lesson was updated with a recurrence count and an escalation note: mechanical enforcement via PreToolUse hook is now overdue. Two failures of the same rule means human discipline lost.
